# 後端輸入驗證

## 目的
前端驗證可被繞過；所有輸入都必須在後端再驗證一次，確保進入業務邏輯與資料庫的資料符合型別、長度、格式與業務規則。

## 規則
- **DEV-SEC-INPUT-001-R1 後端必驗**：前端的必填、長度、格式、範圍檢查，後端都要再檢查一次；直接呼叫 API 也要得到相同的驗證結果。
- **DEV-SEC-INPUT-001-R2 型別與長度**：數字、日期、布林在後端以型別解析，解析失敗回應格式錯誤；字串限制最大長度且不超過資料庫欄位長度。
- **DEV-SEC-INPUT-001-R3 白名單格式**：有固定格式的欄位（身分證字號、統一編號、電話、Email、代碼）以白名單規則（正規表示式或檢核碼）驗證；不以黑名單排除特殊字元。
- **DEV-SEC-INPUT-001-R4 代碼值**：下拉選單、選項、狀態等代碼，後端確認值存在於允許的代碼表，且使用者有權使用；不信任前端只顯示允許的選項。
- **DEV-SEC-INPUT-001-R5 業務規則在後端**：金額、數量、日期區間（起日 ≤ 迄日）、狀態轉換（例如只有「草稿」可送出）、額度上限等業務規則由後端檢查；前端計算的金額或結果只作顯示，後端重新計算。
- **DEV-SEC-INPUT-001-R6 集合與大小**：陣列、清單、上傳筆數限制最大數量（依 `DEV-PAGE-001`）；請求本體限制大小。
- **DEV-SEC-INPUT-001-R7 正規化**：驗證前先去除前後空白並統一全形／半形（依專案規則）；驗證與使用的必須是同一個值。
- **DEV-SEC-INPUT-001-R8 一致的錯誤回應**：驗證失敗回應標準錯誤（依 `DEV-ERR-001`、`DEV-MSG-001`），指出欄位但不洩漏內部資訊。

## 移轉專案
Legacy 只有前端驗證時，Target 於後端補上相同規則，驗證結果與訊息須與 Legacy 前端一致；Legacy 前端也沒有、但為安全必須新增的驗證，標 `REVIEW_REQUIRED`，核准後列為 `APPROVED_BEHAVIOR_CHANGE`。

## 驗證方式
- 每個 API 直接送出：缺必填欄位、超長字串、錯誤型別（`abc` 給數字欄位）、不存在的代碼、起日大於迄日、負數金額、不允許的狀態轉換：都回應驗證錯誤且資料無異動。
- 竄改前端計算的金額後送出：後端以重新計算的結果為準或拒絕。
