日常工作提示詞範例

ADF 安裝好之後，平常就是在 Claude Code（或 Codex）裡用一句話交代工作。以下是貼近實際工作的範例，把【】裡的內容換成你的 Module、檔案或單號就能直接用。

好提示詞的 5 個要素
1. 哪支作業用作業代號界定範圍，例如 modules/S1610（帳號查詢作業）；一次只處理一支作業，避免 AI 擴大範圍。有 Target 程式時一併寫出位置。
2. 什麼工作新功能、修改、修 Bug、弱掃、重構、移轉…對應 NEW／CHANGE＋Intent／MIGRATION。
3. 證據在哪需求文件、JSP 路徑、弱掃報告、會議紀錄、錯誤截圖。沒有證據 AI 只能猜。
4. 範圍與禁區只改哪裡、哪些不能動（例如「不要改 DB schema」「不要寫程式」）。
5. 停在哪一步這次做到哪個 Stage 就停，讓你審查後再繼續，避免一次跑到底。
✗ 太模糊幫我把帳號查詢加一個部門條件。
✓ 可以直接開工用 adf-develop 在 modules/S1610（帳號查詢作業）開一個 CHANGE（FEATURE）：查詢條件新增「部門」，可多選、不選代表全部。需求來源是 Redmine #4821。Target 程式：S1610Controller.java、S1610Query.vue；其他作業不要動。這次只做到 Requirement Delta 與 Rule 更新就停，不要寫程式；不確定的地方一問一答問我。
範圍控制：一句提示詞只對一支作業（例如 S1610）。需求跨多支作業時，拆成各自的 Module 分開下指令；有 Target 程式就寫出檔案或目錄，並註明「其他作業不要動」。沒有 Target（全新或尚未移轉）時，只寫作業代號即可。

每個案例至少留下什麼
案例與預期
記錄 Test ID、來源 REQ-*／BR-*／VAL-*／Q-*／UI-*、輸入、前置資料、權限、Expected Result 及依據。查詢功能須涵蓋條件組合、空值、排序、分頁與邊界。
執行與證據
記錄環境、版本、執行時間、實際輸出、截圖或回應／資料庫結果，以及可重現步驟。移轉比對須保留 Legacy 與 Target 原始結果及正規化依據。
判定與處置
逐例標示通過、失敗或待判；差異記錄分類、原因、修正追蹤與重測結果。不能確認預期時標 UNKNOWN／REVIEW_REQUIRED，必要條件缺失時標 BLOCKED。
結案核對
執行 adf-traceability-check，確認 Source → Rule → Standard → Design → Functional Scenario → Test → Result 可追溯；Regression 與必要 Human Gate 完成後才進行結案。
人工操作起點是 modules/<module-id>/verification/functional-scenarios.md；技術案例對照 verification/test-cases.md；測試與審查狀態再對照 verification/traceability.md、manifest.yaml。勾選 QA 只能輔助盤點，不能產生測試證據。

關鍵字定義與用途
用原套件的識別碼查找含義；中文說明協助判斷何時使用。可搜尋或依類別篩選。
容易混淆的用途
先看判斷依據，再選工作流程或差異類別。
NEW / CHANGE / MIGRATION
三者是 Work Type：分別表示全新、對核准基線修改、舊系統移轉。SECURITY_FIX 與 REFACTOR 是 CHANGE 可搭配的 Intent。
DEV-* / MIG-*
DEV-* 定義 Target 應如何設計；MIG-* 定義 Legacy 到 Target 哪些轉換被允許，並可支持結果正規化。
OBSERVED / APPROVED
OBSERVED 是從 Target 看見的行為；APPROVED 需要有 Evidence 與人工核准，不能由程式現況直接升級。
UNKNOWN / REVIEW_REQUIRED / BLOCKED
UNKNOWN 是無法證明，REVIEW_REQUIRED 是需要人工判斷，BLOCKED 是缺少必要條件而不能繼續；都不等於已核准。
MIGRATION_DEFECT / APPROVED_BEHAVIOR_CHANGE
前者是 Target 未保留應保留的語意；後者是經核准 MIG-* 支持的預期變化。先核對證據，不能只看畫面不同就分類。
SPEC_GAP / LEGACY_UNKNOWN / TEST_DATA_PROBLEM
分別是規格不足、舊行為無法證明、測試資料不可比。各自需要補規格、補舊系統證據、修測試資料。
本版套件的差異分類使用 APPROVED_BEHAVIOR_CHANGE。APPROVED_CHANGE、ACCEPTED_DIFFERENCE、INTENTIONAL_IMPROVEMENT 不是 v5.2.0 的正式分類值；若專案另有用語，應先建立對照並經審查。
各階段檢核點
每個檢核點都要找得到對應文件與證據。出現未解問題時，先處理再送 Human Gate。
高風險問題須逐題確認；低風險問題可以批次確認建議。問題清除後，需人工確認才能將要求 Human Gate 的階段標記 APPROVED。

常見狀況
偵測到既有 ADF 痕跡一鍵安裝在寫入前停止並列出找到的舊檔。這是 v5.0 或手動複製的舊版專案；改選上方「v5.0／手動舊版」，依移轉 SOP 處理。
Installed skill differs from npx lock已安裝的 Skill 被手動改過，更新前 VERIFY 失敗。把客製內容移到 standards/ 或專案外再更新；確定要覆蓋時加 --force（PowerShell：-Force）。
Missing/unsupported formal npx source部分 Skill 仍是舊 tag。重新執行一鍵更新，或手動 npx skills add … --skill '*' 安裝全部 33 支。
更新中途失敗腳本自動還原為更新前版本並重新 VERIFY。還原不完整時，備份路徑會印在畫面上（專案外暫存目錄）。
Windows 無法建立符號連結npx skills 預設使用 symlink。加 -Copy；之後一鍵更新會自動沿用 copy 模式。
Unresolved legacy instruction referenceCLAUDE.md／AGENTS.md 引用了舊 framework 路徑。依 resources.json 修正引用後重新 PLAN；不要略過 blocker。
手動安裝（進階）
需要逐步確認，或一鍵腳本不適用時使用。統一以專案層級 npx skills 管理 33 支 Skill；不要加 -g。
  1. 選真正的專案根目錄。將 Skill、lockfile、指引、standards、modules 與未提交資料備份到專案外。
  2. 先列出正式 tag 的 Skill，再明確選 Agent 安裝全部 33 支；確認 skills-lock.json 的 ref 都是 v5.2.0。
  3. 使用 adf-project-install 執行 CHECK，再 PLAN，計畫輸出保存於專案外。
  4. 處理 blockers：未知／客製範本先人工歸位至 standards 或 modules；修正失效指引引用。
  5. 人工選定計畫後 APPLY；檔案已變動時重新 PLAN。VERIFY 通過、resolve 找得到 core/invariants.md 才宣告完成。
  6. 需要回復時 RESTORE；Skill 與 lockfile 另由安裝前外部備份還原。回到 v5.1 只需用 v5.1.0 tag 重新安裝。
npx skills add https://github.com/chungtsai/adf-framework/tree/v5.2.0 --list
npx skills add https://github.com/chungtsai/adf-framework/tree/v5.2.0 --skill '*' -a claude-code

node <skill-root>/scripts/project.mjs CHECK "."
node <skill-root>/scripts/project.mjs PLAN "." > <專案外plan.json>
node <skill-root>/scripts/project.mjs APPLY "." <專案外plan.json>
node <skill-root>/scripts/project.mjs VERIFY "."
node <skill-root>/scripts/project.mjs resolve "." core/invariants.md
<skill-root> 是本專案實際安裝的 adf-project-install 目錄（Claude Code：.claude/skills/adf-project-install；Codex：.agents/skills/adf-project-install）。Codex 改用 -a codex；Windows 需要實體副本加 --copy。已導入 v5.1 的專案只需重新安裝與 CHECK／VERIFY，不需 PLAN／APPLY。
